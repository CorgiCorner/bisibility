title: "Discovery"
description: "Unauthenticated API discovery endpoints for health checks and agent clients."
---

Discovery endpoints do not require an API key. They are still rate limited by
client identity.

## Liveness and readiness

Use liveness to decide whether to restart the web process:

```http
GET /api/v1/liveness
```

Liveness performs no database, migration, worker, or Temporal checks. A response
means the web process can execute the handler, so it returns `200` even when the
database contract is not ready.

Use readiness to decide whether to send web traffic:

```http
GET /api/v1/readiness
```

Readiness returns `200` only when the database is reachable and blocking data
migrations report `ready`; otherwise it returns `503`. Worker heartbeat,
Temporal, and worker-schema parity do not decide web readiness because reads can
still be served while those asynchronous subsystems are unavailable.

```json
    "default_market": "United States",

      {
        "gl": "us",
        "language_code": "en",
        "language_label": "English",
        "name": "United States"
      }
    ]
  },
  "liveness": "ok",
  "readiness": "ok",
  "services": {
    "app": "ok",
    "appRelease": "0.2.1",
    "appRevision": "0123456789abcdef0123456789abcdef01234567",
    "database": "ok",
    "migrations": "ready",
    "temporal": "ok",
    "worker": "ok",
    "workerRelease": "0.2.1",
    "workerRevision": "0123456789abcdef0123456789abcdef01234567",
    "workerSchema": "ok"
  },
  "status": "ok"

```

`/health` remains the compatibility and diagnostics endpoint. Its composite
`status` still degrades for a database or migration failure, a degraded or down
worker or Temporal service, or worker-schema drift. Use the explicit probe
endpoints for restart and traffic decisions.

`services.appRevision` and `services.workerRevision` identify the public source
revision baked into each artifact. They are `"unknown"` when the build did not
provide `APP_REVISION`. Runtime environment overrides cannot change the reported
revision after the artifact is built.

`services.migrations` answers whether blocking data migrations have finished
with their expected checksums and whether the public ID database contract is
ready. It does not report whether the Prisma schema is current. Run
`npx prisma migrate status` in the deployed application environment to check
schema currency. This known limitation is unchanged from 0.1.0 and is scheduled
to be addressed.

Composite status is `200` when all reported health checks succeed and `503` when
health is degraded.

## OpenAPI

```http
GET /api/v1/openapi.json
```

Returns an OpenAPI 3.1 document generated by `lib/api/openapi.ts`.
Every operation documents the optional `Bisibility-API-Version` request header
and the `409` response returned for an unsupported declared version.

## Capabilities

```http
GET /api/v1/capabilities
```

Response:

```json
{
  "apiVersions": ["v1"],
  "data": [
    {
      "name": "listKeywords",
      "operationId": "listKeywords",
      "description": "List project keywords",
      "input_schema": {
        "type": "object"
      }
    }
  ]
}
```

`apiVersions` is the set of API contracts this server serves. It belongs here
because capabilities is the machine-readable contract discovery surface.
`/health`, `/liveness`, and `/readiness` remain operational probes and do not
duplicate API compatibility state.

Capabilities are derived from the OpenAPI operation ids and the agent-facing
tool input schemas in `lib/api/capabilities.ts`.

These camelCase names are REST/OpenAPI operation identifiers. MCP clients use
the separate unprefixed snake_case tool names advertised by `/api/mcp`, such as
`list_keywords`.

## API version declaration

A client can opt into the advertised contract by sending:

```http
Bisibility-API-Version: v1
```

The product-namespaced header avoids collisions with unrelated API version
headers and does not use the deprecated `X-` convention. A request with no
header, or an empty header, is undeclared and follows the existing request path
without version negotiation. This keeps clients deployed before version
declarations were introduced working unchanged.

If a client declares a version that is not in `apiVersions`, the server returns
`409 Conflict` before authentication, rate limiting, or request parsing:

```json
{
  "type": "https://bisibility.com/problems/unsupported_api_version",
  "title": "Unsupported API version",
  "status": 409,
  "detail": "The declared API version v2 is not served by this server.",
  "instance": "urn:bisibility:api:v1:/api/v1/projects",
  "docs_url": "https://bisibility.com/docs/api/errors#unsupported_api_version",
  "errors": {
    "apiVersions": ["v1"],
    "declaredApiVersion": "v2"
  }
}
```

## Provider rates

```http
GET /api/v1/provider-rates
```

Returns provider pricing inputs used by the public rank-tracking cost estimator.

## Cost estimate

```http
GET /api/v1/cost-estimate
```

Returns an anonymous cost estimate for a provider, keyword count, location count,
device count, schedule, and organic result depth. Pass `depth=10`, `20`, `50`, or
`100`; omitted depth defaults to `100`.

## llms.txt

```http
GET /api/v1/llms.txt
```

Returns a plain-text summary with the API base URL, auth scheme, resources, and
tool names.
