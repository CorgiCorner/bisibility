A project is the unit of keywords, providers, and rank history. This page covers
behavior that the generated API Reference does not: which credential can see or
create a project, how missing projects are hidden, and how defaults move
keywords.

## Credentials

<span id="list-projects"></span>

Project API keys are scoped to one project, so `listProjects` returns only that
project and `createProject` remains forbidden for them. A personal access token
returns every project the user belongs to and can create a new one when its
tier is at least `write`.

`project_id` must be the public `prj_...` id. If the project does not match a
project key, the API returns `403`. A PAT gets `404` when the user is not a
member, so project existence is not disclosed.

Only an owner's PAT can call `deleteProject`; project API keys receive `403`.

Provider accounting evidence is retained separately after project deletion so
late receipts and duplicate requests can still be reconciled against their
original owner. It contains identifiers, request source, timestamps, quantities
and costs, without keywords, response content or provider secrets. This evidence
currently has no automatic expiry; deleting a project does not erase it.

Self-hosters may cap the number of projects owned by one user with
`BISIBILITY_MAX_PROJECTS_PER_USER`. Current hosted limits live in
[Deployment options](/deployment-options).

## Project overview

`getProjectOverview` returns numeric health aggregates without paginating the
keyword list. `range` defaults to `28d` and accepts `7d`, `28d`, or `90d`.
`device` defaults to `all` and also accepts `desktop` or `mobile`. `tag` is an
optional exact tag name. The comparison uses the latest qualified observation at
or before the start of that range, within the retained policy tolerance; it is
not a period average. Missing or incompatible baseline evidence returns `null`.

The endpoint uses the authenticated project key or personal token and requires
no browser session. Credential and project access are checked again when reading
measurement definitions. It reads retained observations without starting checks.

Positive `average_position_delta` means the average rank improved. Visibility
measures volume-weighted ranking strength in Google's Top 20. A value of 100
means every measured keyword ranks #1. Rankings below #20 do not add Visibility,
and shallow or failed checks are not treated as lost rankings.
`visibility_delta` is measured in percentage points. Rank aggregates and
distribution counts are `null` when no qualified observations are available.
A proven absence within a complete checked range contributes a real count `0`;
missing, failed or incomplete observations do not establish absence.

## Project defaults

`getProjectDefaults` returns the effective market, device and inherited SERP depth.
Projects without a stored defaults row return a market inferred from existing
keywords, without creating a row. The `source` field is `explicit`, `derived`,
or `fallback`.

`updateProjectDefaults` changes these defaults without enrolling keywords in
recurring checks. `location_key` is the primary location reference and can point
at a country, region, or city; send it with `device` to move eligible keywords
from the current default market to the new market.

The legacy `country` and `city` selectors still resolve to the same location,
but they are deprecated: send `location_key` instead. `country` and `device`
must be supplied together unless `location_key` is provided. Omitting market
fields does not move keywords. Omitting `serp_depth` (`10`, `20`, `50`, or `100`)
or `serp_stop_on_match` keeps its stored preference. At effective depth `20`,
checks always collect the full requested depth and the effective
`serp_stop_on_match` is `false`. The preference still applies at other depths.
This does not guarantee twenty returned organic results: provider gaps remain
unknown and do not establish absence.

The compatibility fields `frequency`, `cron_expression`, `jitter_minutes` and
`timezone` are deprecated and ignored on writes. Reads return `manual`, `null`
and `0` for the first three, with `next_check_at: null`; `timezone` retains its
stored value. Use named schedules to configure cadence and assign keywords.
New keywords without a schedule remain manual.
