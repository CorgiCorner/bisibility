# Recurring Local monitor authority

Recurring Local execution is off unless `LOCAL_MONITOR_RECURRING_ENABLED=true` (or `1`) is explicitly configured. `SCHEDULER_DRIVER=none` cannot activate it. The existing worker-intent processor owns due production and the existing Local workflow owns provider submission and collection. There is no additional cron, browser-triggered purchase or inline fallback.

A project writer chooses an existing calendar and own-key connection, a per-occurrence USD ceiling, a total issuance ceiling, a maximum number of measurements and an approval end. Preview resolves current registered capability and native quote from the database. Confirmation verifies the signed snapshot and records the immutable recurring approval with the existing append-only schedule intent in one transaction. Reading the page never quotes, materializes targets, reserves money or calls a provider. A viewer can read but cannot approve or pause.

The approval freezes subject/identity, definition, canonical points, surface/device/keyword epoch target set, effective calendar/timezone, credential custody stamp and code/price version. Each due occurrence receives a fresh quote under this explicitly approved recurring policy. It must match the frozen scope/version and fit both ceilings. An old quote is never extended. Original quote expiry still applies between queue acceptance and first send. A source, calendar, credential, actor-access, definition or price-version change requires review rather than silent rebinding.

The total ceiling tracks conservatively issued exact quotes, not actual settled spend. An issued quote continues to consume this authority even if admission later fails or native unfenced cleanup proves that nothing was sent. Actual Meter project/connection budgets and retained financial states remain independent mandatory admission gates. Unknown cost or acceptance is never zero.

The planner supplies occurrence identity and timezone/DST behavior. Completely elapsed calendar intervals are skipped without buying a backlog. Manual and scheduled work share the same target owner and native admission locks. A retained pending/unknown owner or unprocessed queued job prevents another purchase. Each workflow receives only its opaque intent ID and derives authority from persisted data; a linked run is recovery-only and cannot reconstruct a first-send grant.

Pause appends a new schedule intent and blocks future first-send authority. It does not erase history, discard possible-send evidence, refund unknown work or stop retrieval of original accepted IDs. Archive, deployment disablement and access revocation obey the same separation. Only native unfenced proof can release an unsent reservation.

First-send validation commits the native Meter fence and the Local possible-send marker in the same transaction. Rejected validation or a failed projection leaves both unfenced; no provider request is made. After that transaction, a lost commit response, read failure or expired quote remains possible-send uncertainty. A restart cannot recreate the first-send permit.

An older pre-fence marker can be cancelled only after fresh authorization, expired execution ownership, original custody verification and actual native unfenced cancellation. Recovery retains its original attempt identifier. Outcome, collection, settlement or reconciliation evidence excludes this path. The worker sends genuinely fenced work to original reconciliation; timeout or a missing response never proves zero cost. A retained cancellation is terminal only after reading its original native release or exact Meter no-send settlement and discarded evidence. Its financial state keeps the native `released` or `settled` value.

Acceptance requires actual migrations and immutable/FK/cursor checks, native financial/claim/crash tests, real Temporal execution with a synthetic provider and product inspection under the current browser policy. The source packet's fake tests and syntax projection are partial validation. No operator configuration or deployment is activated by installing the source.

## Saved results and history

The run-history selector offers the last7,28 or90 elapsed days ending at the saved report time, or all retained history. These are24-hour durations, not daily aggregates. Dates display in the report timezone. Canonical `from` and `to` timestamps are inclusive and select original occurrence capture time; the signed `asOf` remains fixed. Deep links and subsequent pages retain that interval. Changing it resets the selected run to the latest available run in that interval.

Point history uses the exact captured target, including its immutable keyword, grid, identity and policy. The first page contains at most20 attempts; load earlier attempts to continue through the selected interval. Every page rechecks project and entity access. A changed interval, altered retained source or revoked access invalidates continuation. More than1000 retained runs/items is an explicit capacity refusal; narrow the interval instead of treating a truncated result as all history. Reading, paging and exporting use retained data and do not submit a scan or change schedules.

Freshness uses the current explicit project policy together with the original intent linked to each occurrence. A manual run uses configured manual TTL; scheduled runs use two successor slots of their captured monitor calendar plus configured tolerance, preserving real timezone/DST/jitter behavior. Missing policy or original calendar stays unknown. A stale positive rank remains visible with its real observation time, while fresh coverage excludes it. JSON/CSV manifests include the policy epoch, configuration revision and basis; this describes evaluation now, not proof that today's policy existed at the old observation time.

The staged pilot permits1×1,3×3 and5×5 definitions and first-send preparation, subject to the existing explicit quote and budget gates. Retained7×7 geometry/history remains readable; larger grids require a separate scope/budget pilot decision before new authoring or execution. Already accepted runs retain collection and recovery authority.

## Connection configuration and upgrade consent

Usage timestamps and background synchronization do not change a connection's approved configuration. Local consent binds the connection's semantic configuration and credential revision, including rate edits and configuration changes that are later reversed. Definition, calendar, scope, price and capability checks remain independent.

After upgrading from timestamp-based connection stamps, request a new preview and explicitly approve future measurements. Older approvals and queued first-send commands do not silently adopt the new stamp. Previously blocked monitors stay blocked until reviewed; upgrading does not enable a schedule. Original accepted tasks retain their existing collection and accounting recovery path.


## Matcher version compatibility

New business decisions use `business-match-v2` or `business-match-maps-v2`, which separates proven paid appearances from organic identity ambiguity while unknown promotion remains potentially organic. Existing v1 decisions remain immutable and readable under their original version; accepted task recovery verifies those retained decisions without rematching. Reports preserve the stored matcher version in evidence and comparison keys. Different matcher versions do not form one comparable series. A grid collected across a matcher upgrade retains every point and receipt, but its ranking rate and sample bounds are unavailable with `matcher_version_mixed`. Coverage and counts stay factual; homogeneous grids in the same run remain available. A new version does not trigger historical rematching, provider requests or schedule activation.
